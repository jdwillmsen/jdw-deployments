# 2026-09-15 — Bedrock version checks stopped when Mojang changed the default transport

| | |
|---|---|
| **Workload** | minecraft-fwb (`jdwillmsen-prd`) |
| **Detected** | 2026-09-15 17:01 UTC by alert; acted on 21:15 UTC |
| **Resolved** | 2026-09-15 21:25 UTC, when the server was updated to 1.26.51.1. Not recognised as resolved until 2026-09-16 00:36, after a detour through NetherNet that was unnecessary |
| **Data loss** | none |
| **User impact** | Players could not join from roughly 15:00–16:00 UTC, when Mojang pushed 1.26.51 to clients, until the transport switch. Multiple user reports. Automatic version tracking was off for the same window. |

## Summary

The hourly `version-check` CronJob boots a throwaway copy of the server image to
learn what `LATEST` resolves to, then compares that against production. It
learned the answer by pinging the candidate with `mc-monitor status-bedrock`.
Bedrock 1.26.51 changed the default in a freshly generated `server.properties`
to `transport=nethernet`, and a NetherNet server opens no RakNet listener at
all — so the ping could never succeed, the job exited before reaching its
compare-and-restart branch, and every run failed from 16:00 UTC onward.

## Impact

No data loss. The cost was a player-facing outage, and the stale automation is
why it lasted.

Retail clients auto-updated to 1.26.51 when Mojang published it. A 1.26.45
server rejects them, so from that moment nobody could join. The last human
session ended 07:39 UTC and none began again — every connection in the log
afterwards is a Go library client. The check that would have caught the new
version and restarted the server onto it failed for the first time at 16:00
UTC: the same release, the same cause.

Updating the server to 1.26.51.1 was necessary but not sufficient. That release
also makes NetherNet the only transport retail clients will use, and the server
was still on RakNet — so it answered the server-list ping, accepted the Go
bots, and remained unjoinable. That failure mode looks healthy from every
direction this repo monitors.

Six consecutive check runs failed. The failure path is loud (see Detection), so
the cost was not silence; it was four hours of firing alerts that nothing acted
on while players could not play.

The candidate reached `Running` and the server inside it started — the phase in

retried a candidate that was working exactly as designed.

A probe pod built from the same spec (21:16) reproduced it immediately:


while that same pod's log claimed it was up:

```
[2026-09-15 21:16:35:009 INFO] Accepting clients on [::]:19132
[2026-09-15 21:16:36:423 INFO] Server started.
```

`/proc/net/udp` and `/proc/net/udp6` inside the probe showed no socket on
19132 in either family, and a ping from another pod over the pod network was
refused the same way. The server was running and listening for nothing that
speaks RakNet.

## Root cause

`server.properties` generated fresh by 1.26.51.1 contains:

```
transport=nethernet
```

The same file generated by 1.26.45.1, from an otherwise identical pod spec,
contains `transport=raknet`. NetherNet is signalled over Microsoft's service
rather than accepting RakNet UDP, so the candidate opens no port for
`mc-monitor status-bedrock` to reach.

The candidate always mounts an empty `emptyDir` at `/data` — that is the point
of it, since `VERSION` must be left at its default for `LATEST` to be resolved
fresh. So the candidate always gets the *current release's* defaults, which is
precisely the thing a version check cannot afford to have opinions about.

Production was unaffected only by accident: its `server.properties` lives on
the world PVC and was generated by an older build, so it still carries
`transport=raknet`. The chart sets `transport` nowhere.

## Contributing factors

- The check's liveness test and its actual question were conflated. It only
  ever needed the version string; requiring a serving RakNet endpoint to get it
  coupled the check to a protocol detail that Mojang owns.
- The same coupling exists in `ci.yml`'s boot smoke test, which gates Renovate
  image bumps on `mc-monitor status-bedrock` answering. It would have failed on
  the next bedrock image bump for the same reason. Fixed in the same PR.
- `failedJobsHistoryLimit: 5` and the job TTL mean the visible evidence window
  is roughly five hours; the first failing run was recovered from Prometheus,
  not from the cluster.

## Hypotheses considered and rejected

| Hypothesis | Why it looked right | What disproved it |
|---|---|---|
| The 60s poll budget is too short for a cold candidate | The failure message is a timeout, and the job has a history of deadline arithmetic being wrong | A control probe on 1.26.45.1 answered in ~5s from the same spec; the 1.26.51.1 probe was still refusing connections after 160s |
| Transient Mojang/DNS failure, the case the two-attempt retry exists for | Both attempts failed identically, which is what a resolver blip looks like | It repeated across six consecutive hourly runs, and the candidate's own log shows the download and boot succeeding |
| Production is one restart away from the same fate | The chart sets no transport, and the candidate proves what the current default is | Production's PVC carries `transport=raknet`; after the manual update it logged `IPv4 supported, port: 31132` and clients connected. It is inherited, not configured — see the register |

## Detection

The alerting worked. `CronJobLastRunDidNotSucceed` fired at 17:01,
`KubeJobFailed` at 17:02, and the workload's own
`JdwillmsenMinecraftVersionCheckStale` at 19:00. The ArgoCD Application went
`Degraded`.

Nothing acted on any of it for four hours, and the investigation started from a
human asking why the server had not updated. The gap here is response, not
instrumentation.

## Resolution

Service was never down; the update was applied by hand.

1. Reproduced with two probe pods differing only in `VERSION`, isolating the
   transport default as the single variable.
2. Took a fresh backup ahead of the world upgrade, which is one-way:
   `fwb-20260915T212325Z.tar.gz`, 594754033 bytes, `quiesced=1`.
3. Announced the restart in game.
4. Deleted the StatefulSet pod at 21:25:09; it came back Ready at 21:25:47 on
   1.26.51.1, logging `IPv4 supported, port: 31132`.
5. Verified real joins rather than trusting the banner (see below):
   `Player Spawned: Dotablaze7321` and `Player Spawned: JDWServerAgent`.

6. Moved production onto NetherNet at 22:14 — **which was not necessary and
   should not have been done.** RakNet was never shown not to serve retail
   clients; it was assumed from the startup banner. A real client could not
   join over NetherNet either, and the switch took the server agent and both
   AFK bots offline for 104 minutes, because they have no NetherNet client.
7. Reverted to `transport=raknet` at 23:53 and restored the probes and all
   three replicas. A retail client joined successfully at 00:36:

   ```
   [2026-09-16 00:36:19] Player connected: Dotablaze, xuid: 2535473803383948
   [2026-09-16 00:36:22] Player Spawned:  Dotablaze
   ```

   That is the first retail join since 07:39 on 2026-09-15, and it confirms the
   version update at 21:25 had already fixed the outage.

1.26.51 prints, at ERROR level, on a RakNet server:

```
[2026-09-15 21:25:28:636 ERROR] Your current connection type is not set to NetherNet. In this release, NetherNet is the only supported transport type.
[2026-09-15 21:25:28:636 ERROR] Players will not be able to connect to your game without NetherNet.
```

**That message is not true of this release, and acting on it cost more than
the outage did.** Retail clients still join over RakNet on 1.26.51 — verified
at 00:36 by a real client, on a server that had printed this banner at every
start. Treat it as notice that a future release will remove RakNet, not as a
description of this one.

The reasoning that went wrong is worth stating plainly, because the individual
steps were each defensible. Two Go clients joined over RakNet right after the
upgrade. That was correctly identified at the time as proving nothing —
gophertunnel implements RakNet itself and is unaffected by any client-side
change. But the conclusion drawn from "this evidence is worthless" was "so the
banner must be right", when the available move was to spend two minutes asking
a human to try joining. The version-matched RakNet server was never tested by a
client before it was replaced.

Every component this repo runs against the server — the mc-monitor sidecar,
the console bridge, the server agent and both AFK bots — speaks RakNet only.
`transport` is a single value, so the switch took all of them down; the farm
stopped loading chunks for 104 minutes and bought nothing.

## Assumptions invalidated

- A Bedrock server that logs `Server started.` is answerable by
  `mc-monitor status-bedrock`.
- Production's transport is a configured property. It is an artifact of when
  its `server.properties` was first generated, and survives only because the
  PVC does.
- A client connecting proves the server is joinable. Every client that
  connected during this outage was a Go library client implementing RakNet
  itself; none of them could have detected what was wrong.
- The monitoring covers "can players play". It covered "does the server answer a
  RakNet ping", which stayed true for the whole outage. As of 2026-09-19 a probe
  asks the next question — will the server start a session — and the agent's own
  session recycle asks the one after it, whether a real account can reach spawn.
- A vendor's own startup banner describes the release it ships in. 1.26.51
  states NetherNet is "the only supported transport type" and that players
  cannot connect without it. Retail clients joined over RakNet on that exact
  build. The banner is a deprecation notice written in the present tense.
- Ruling out the evidence you have is the same as having evidence for the
  alternative. It is not. Once the Go clients' joins were correctly discarded
  as proof, the honest position was "untested", and the test was two minutes of
  a human's time.
